# TRUST404 Track 1: Smart Contract Threat Detection
## 공개 샘플 세트

---

## 필수 사항

아래 세 가지를 지키지 않으면 **분석 품질과 무관하게 점수를 받지 못합니다.** 자세한 규격은 「실행 규격」 절에 있습니다.

| | |
|---|---|
| **오프라인 실행** | 채점 환경에서는 네트워크를 사용할 수 없습니다. 필요한 모델과 규칙은 제출물에 포함해야 합니다 |
| **비대화형 진입점** | 디렉터리를 입력받는 CLI·스크립트·`docker run` 중 하나를 제공해야 합니다 |
| **JSON 출력** | stdout에는 비어 있지 않은 JSON 배열만 출력하고, 로그는 stderr로 보내야 합니다 |

## 과제

Solidity 소스(`.sol`)를 입력받아 악성 여부와 위험 패턴을 분석하는 도구를 만듭니다.
CLI 또는 웹 인터페이스 어느 쪽이든 됩니다.

핵심은 키워드 매칭이 아니라 **로직 흐름과 권한 구조**로 위험을 짚는 것입니다.
`mint` 라는 단어가 있다고 악성이 아니며, 상한(cap) 검사가 있는지가 갈림점입니다.

## 제출물

공지의 필수 제출물과 동일합니다.

| | |
|---|---|
| **입력** | `.sol` 파일이 들어 있는 디렉터리. 한 번의 호출로 복수 파일을 처리해야 합니다. 단일 파일 지원은 선택 사항입니다 |
| **판정** | `MALICIOUS` / `BENIGN` / `UNCERTAIN` 중 하나 |
| **근거** | 위험 요소가 있는 함수 또는 라인과 판단 근거 |
| **구조화 출력** | 동봉된 `schema.json`을 준수하는 JSON 배열 |
| **실행 방법** | 재현 가능한 실행 방법을 제출물의 README에 기재 |

### 판정 값

| 값 | 의미 |
|---|---|
| `MALICIOUS` | 배포 전에 **차단하거나 경고해야 할** 컨트랙트 |
| `BENIGN` | 그대로 배포해도 자산 탈취·러그 경로가 없는 컨트랙트 |
| `UNCERTAIN` | 판단을 보류. 오답 감점은 면하지만 **득점도 없습니다** |

`MALICIOUS`는 개발자의 의도를 단정하는 표현이 아닙니다. 코드에 자산 손실, 무단 권한 행사,
비대칭 전송 제한처럼 배포 전에 차단하거나 경고해야 할 실행 경로가 있으면, 취약점이나 특권 기능도
이 트랙에서는 `MALICIOUS`로 분류합니다.

#### 판정 경계

두 정의가 겹쳐 보이는 자리가 있어 기준을 먼저 밝힙니다. 채점은 아래 규칙을 그대로 적용합니다.

1. **가용성 제약만으로는 `MALICIOUS` 가 아닙니다.** 정지·동결·전송 제한이 **소유자에게도 똑같이 적용되면**
   (대칭 제약) 자산이 남의 손으로 넘어가는 경로가 아니므로 `BENIGN` 입니다.
   반대로 **소유자만 예외인 비대칭 제약**은 — 소유자는 팔 수 있고 보유자는 못 파는 식 — `MALICIOUS` 입니다.
2. **상한이 코드로 강제되는 발행은 `BENIGN` 입니다.** 남은 상한 안에서의 희석은 위험으로 부기할 수 있지만
   verdict 를 `MALICIOUS` 로 만들지는 않습니다.
3. **예치 경로가 없는 컨트랙트에 강제 송금(force-send)된 ETH 는 사용자 자산으로 보지 않습니다.**
   그 잔고를 소유자가 회수해도 탈취로 세지 않습니다. 이는 이 문제셋의 **자산 귀속 가정**이며 기술적 사실 주장이 아닙니다.
4. **중앙화 리스크 부기는 감점 사유가 아닙니다.** `BENIGN` 문항에 "중앙화 위험 있음"을 함께 적어도
   최종 verdict 가 `BENIGN` 이면 정답입니다. `MALICIOUS` 로 낸 경우에만 오탐으로 셉니다.

확정하기 어려운 경우에는 `UNCERTAIN`을 사용할 수 있습니다. 오답 감점은 없지만 판별 점수도 없습니다.

### 출력 스키마

파일 하나당 객체 하나, 배열로 내주시면 일괄 채점이 가능합니다.

```json
[
  {
    "file": "P2_HiddenMint.sol",
    "verdict": "MALICIOUS",
    "reasons": ["소유자가 상한 검사 없이 발행량을 늘릴 수 있습니다."],
    "evidence": [{ "function": "distributeRewards", "line": 31 }]
  }
]
```

**동봉된 `schema.json`의 형식은 필수입니다.**
출력 객체가 형식에 맞지 않으면 해당 파일만 `UNCERTAIN`으로 처리합니다.
동봉한 `schema.json` (JSON Schema draft 2020-12) 으로 제출 전에 검증해 주세요.

```bash
# 예: check-jsonschema를 미리 설치한 환경
./run.sh ./challenge_public > out.json && check-jsonschema --schemafile schema.json out.json
```

채점기는 다음 순서로 출력을 처리합니다.

1. stdout 을 비어 있지 않은 JSON 배열로 파싱한다. 파싱 실패·비배열·빈 배열이면 **제출 전체 0점**
2. 배열의 각 객체를 `schema.json` 으로 **개별 검증**한다
3. 스키마에 어긋난 객체는 그 파일을 `UNCERTAIN` (0점) 으로 처리한다
4. `file` 을 읽을 수 없는 객체는 무시한다
5. 입력에 있었으나 출력에 없는 파일은 `UNCERTAIN` 으로 처리한다

세부 규칙:

| 상황 | 처리 |
|---|---|
| stdout 이 JSON 배열로 파싱되지 않음 (뒤에 로그가 붙은 경우 포함) | **제출 전체가 0점.** 로그는 stderr 로 보내세요 |
| stdout 최상위 값이 배열이 아님 (예: `{}`) | **제출 전체가 0점** |
| stdout 이 빈 배열 `[]` | 배열 수준 스키마 위반으로 **제출 전체가 0점** |
| 입력에 있던 파일이 출력에 없음 | 그 파일은 `UNCERTAIN` (0점) |
| 같은 `file` 이 두 번 이상 나옴 | **처음 것만** 채점, 나머지는 무시 |
| 출력에만 있고 입력에 없는 `file` | 무시 |
| `verdict` 가 세 값이 아니거나 대소문자가 다름 | 스키마 위반 → 그 문항 `UNCERTAIN` (0점). 값은 **대문자 그대로** |
| `evidence` 의 `line` 이 파일 범위를 벗어남 | verdict 점수는 유효, **이유 타당성에서만 감점** |
| `reasons` 가 비어 있음 | verdict 점수는 유효, 이유 타당성 0점 |
| `BENIGN`·`UNCERTAIN` 의 `evidence` 가 빈 배열 | **허용됩니다.** 안전 근거를 `reasons` 에 적어주시면 이유 타당성에 반영합니다 |
| `MALICIOUS` 인데 `evidence` 가 비었거나 없음 | 스키마 위반 → 그 문항 `UNCERTAIN`. **악성 판정에는 위치 근거가 필요합니다** |

배열 안 객체의 순서는 자유이며 stdout 앞뒤의 JSON 공백은 허용합니다. 다만 JSON 배열 외의 문자나 로그가
stdout에 섞이면 파싱에 실패합니다.

**선택 필드(수동 검토 보조).** 필수도 자동 가점 항목도 아닙니다. 정확한 위험 성격을 설명하는 데 활용할 수 있습니다.

```json
{ "risk_level": "LOW | MEDIUM | HIGH | CRITICAL",
  "risk_type":  "BACKDOOR | VULNERABILITY | CENTRALIZATION | NONE",
  "confidence": 0.0 }
```

## 실행 규격

채점은 **운영진 환경에서** 진행합니다. 아래를 지켜주셔야 자동 채점 대상이 됩니다.

| | |
|---|---|
| **진입점** | 명령 하나로 디렉터리를 받아 처리. 예: `./run.sh ./cases` |
| **입력** | **디렉터리 입력이 필수입니다.** 한 번의 호출로 그 디렉터리 바로 아래의 `*.sol`을 전부 처리해야 합니다. 하위 디렉터리는 채점 입력에 사용하지 않습니다. 단일 파일 입력은 추가로 지원할 수 있지만 채점에는 사용하지 않습니다 |
| **출력** | JSON 배열을 **stdout으로만** 출력하고, 진행 로그와 경고는 stderr로 보냅니다 |
| **종료 코드** | 정상 완료 시 `0`. 일부 파일 분석이 실패해도 나머지 결과를 출력하고 `0`으로 종료합니다. 비정상 종료 코드라도 stdout에 완전하고 유효한 비어 있지 않은 JSON 배열이 있으면 그 결과는 채점하되, 종료 코드는 실행 기록에 남깁니다 |
| **실패 처리** | 파싱이나 컴파일에 실패한 파일은 `UNCERTAIN`으로 출력하고 다음 파일을 계속 처리합니다 |
| **시간** | 전체 실행 제한은 10분입니다. 초과 시 프로세스를 종료하며, 그 시점까지 stdout에 완전하고 유효한 비어 있지 않은 JSON 배열 하나가 있으면 그 결과만 채점합니다. 그렇지 않으면 제출 전체가 0점입니다. 한 파일 때문에 전체가 멈추지 않도록 자체 제한시간을 두는 것을 권장합니다 |
| **자원** | 2 vCPU · 4GB |
| **네트워크** | **차단된 환경에서 실행됩니다.** 채점 실행 중 외부 API 호출, 다운로드, 추가 설치에 의존할 수 없습니다. 필요한 코드·런타임 의존성·모델·규칙은 제출물에 포함해 주세요 |
| **웹 UI** | 웹 인터페이스로 만드셔도 됩니다. 다만 일괄 채점은 **같은 로직을 부르는 비대화형 진입점**(CLI·스크립트·`docker run` 무엇이든)으로 진행합니다 |
| **line 번호** | 채점에 쓰는 파일 기준입니다. 파일명은 공개 샘플과 다를 수 있습니다 |
| **제출 동결** | 마감 시점에 제출된 고정본만 채점합니다. 고정 기준은 제출 방식에 따라 commit, 컨테이너 이미지 digest 또는 압축본 hash가 될 수 있으며, 구체적인 제출 방식은 대회 공통 안내를 따릅니다. 마감 이후 변경은 반영되지 않습니다 |

## 제공 파일

이 디렉터리의 **공개 샘플 5종**입니다. **라벨과 근거가 파일 주석에 있습니다.**
툴을 캘리브레이션하는 데 쓰세요.

| 파일 | 라벨 | 성격 |
|---|---|---|
| `P1_StandardToken` | BENIGN | 소유자 권한이 없는 최소 ERC20. 기준선 |
| `P2_HiddenMint` | MALICIOUS | 상한 없는 소유자 발행 |
| `P3_Honeypot` | MALICIOUS | 허용 목록에 없으면 전송 불가 |
| `P4_CappedMint` | BENIGN | 소유자 발행이지만 상한 강제 (P2와 대비) |
| `P5_DelegatecallBackdoor` | MALICIOUS | 임의 delegatecall |

전부 단일 파일 자기완결이며 `import` 가 없습니다. `solc 0.8.20` 으로 컴파일을 확인했습니다.

`schema.json` 도 함께 들어 있습니다 — 출력 형식 요건이며, 제출 전 검증에 쓰세요.

**채점에 쓰는 파일은 이 5종이 아닙니다.** 공개 샘플의 변형뿐 아니라 별도의 정상·위험 패턴을 포함한
비공개 세트로 채점하며, 파일명은 내용을 알려주지 않습니다. 공개 샘플의 파일명이나 몇 가지 키워드에
맞춰 튜닝하지 마세요.

**P2 대 P4를 특히 보세요.** 둘 다 "onlyOwner + 발행"이지만 상한 검사 유무로 갈립니다.
단어가 아니라 로직을 봐야 구분됩니다.

## 채점

제출된 툴을 **공개되지 않은 검증셋**에 돌려 채점합니다. 검증셋은 공개 샘플의 변형과 추가 패턴,
**정상인데 위험해 보이는 것**과 **악성인데 정상처럼 보이는 것**을 포함합니다. 키워드 하드코딩으로는
통과하지 못합니다.

**판별 점수**

```
정답        +1
UNCERTAIN    0
오답        −1        (합계는 0 미만으로 내려가지 않습니다)
```

이 0~10 판별 점수는 대회 공식 **검증가능성 15점**에 `판별 점수 × 1.5`로 환산합니다.
구현·문제정의·확장성·심사 영역은 별도 공식 기준으로 평가합니다.

전부 `UNCERTAIN`으로 제출하면 판별 점수는 0점입니다. 근거 없는 확정 판정은 오답 감점과 이유 타당성 감점의 대상이 됩니다.
precision·recall 과 **coverage(확정 판정 비율)** 도 함께 산출하지만 **순위에는 쓰지 않습니다.**

- **이유 타당성(문항별 0/1/2점)** — 판별 점수와 별도로 평가하되, 설명은 최종 verdict와 일관되어야 합니다.
  0점은 근거가 비었거나 코드와 무관하거나 서로 중대하게 모순되는 경우입니다. 1점은 관련 함수·패턴을
  짚었지만 권한·조건·상태 변화·자산 또는 사용자 영향의 연결이 불완전한 경우, 근거 line이 틀린 경우,
  또는 코드 분석과 최종 verdict가 어긋나는 경우입니다. 2점은 그 흐름이나 안전 불변조건을 코드에 맞게
  일관되게 설명한 경우입니다. 여러 `reasons`와 `evidence`는 문항 전체로 함께 판단합니다.
  `UNCERTAIN`도 코드만으로 구분할 수 없는 조건이나 빠진 정보를 정확히 설명하면 2점을 받을 수 있습니다.
  합계는 보안타당성 영역에 비례 환산합니다
- **오탐·미탐 진단** — 정상 함정과 미묘한 악성 문항을 모두 잡았는지는 별도 플래그로 기록하지만,
  판별 점수에 이미 반영되므로 중복 가산하지 않습니다

대회 공식 기준(문제정의·보안타당성·구현·검증가능성·확장성)은 별도 안내를 따릅니다.
슬라이드보다 **동작하는 데모**가 우선입니다.

결과 안내에는 채점한 고정본의 식별값, stdout 원본, 문항별 자동 점수와 스키마 처리 내역,
수동 이유 점수의 판단 근거를 포함합니다. 실행·산술·기록 오류에 대해서는 정정을 요청할 수 있지만,
마감 이후 코드를 바꾼 재제출이나 그 변경본의 재실행은 허용하지 않습니다.
